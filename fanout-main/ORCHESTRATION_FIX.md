# 智能编排 409 排查与升级

修复版本：`v3.1.2-orchestrate20261018`，2026-10-18。

## 根据 VPS 实际输出确认的原因

用户确认 VPS 上运行的是 `v3.1.1-repair20261018`。状态接口返回 `running=true`、`stage=busy`、候选 5,159、完成 0、当前 JP；同时日志仍有健康检查与重连，说明整个服务没有停止。

源码与现象吻合：一个国家的全部候选都测完之后，原代码才统一更新完成计数。真实 OpenVPN 握手每个候选有超时，大量日本候选让任务长时间占用。期间再次触发接口返回 HTTP 409，而且重复的后台调用会把原任务的阶段与提示覆盖成 busy。前端只读取 error 字段，漏掉服务器 message，最终显示“智能编排失败 HTTP 409”。

重启前日志中的“槽位已满，上限 150”属于旧进程，不是当前版本仍使用 150 的证明。当前恢复的旧槽位编号可超过 40，因此容量检查也需要将旧编号计入总占用。

## 本次修改

- 原子领取编排锁，在启动后台协程前发布任务状态，避免检查后再启动的竞争窗口。
- 已有任务时返回 202 和原任务进度，前端直接显示当前任务；重复调用不再覆盖任务状态。
- 前端兼容旧服务返回的 busy/409，并保留其他错误的正常报错；正确显示 message。
- 每次最多预检 64 个候选，每国最多 16 个，最多同时运行 4 个预检；每完成一个立即更新计数。
- 满槽时结束编排并给出明确原因，不继续遍历全球候选，也不把容量问题记成节点失败。旧高编号槽位同样计入总容量。
- 移除编排启动时自动删除“冗余/孤儿入站”的步骤，保留已有入站和绑定配置。
- Xray 配置验证增加 15 秒超时，避免外部校验永久占用面板锁。
- 前端统一编排轮询计时器、防止请求重叠，关闭窗口停止轮询；启动数量与后端限制一致。
- 提供 `upgrade-local.sh`，在现有 systemd 安装上先校验版本和二进制 SHA-256、备份程序与运行目录，再仅替换 fanout 并重启服务；启动失败回滚程序，不主动重写配置。

限制候选数量意味着每轮只检测有限样本，不能承诺一轮覆盖所有国家；节点不足时可以待冷却后再次编排或调整来源。

## 验证

100 项 Go 顶层测试通过，包括新增的并发单任务领取、busy 请求保留进度、并发 HTTP 请求返回 202、满槽零预检退出、旧编号计入容量与全局分配上限测试。前端测试覆盖旧 409 与新 202 的兼容，并保持其他 409 为错误。

Windows/amd64 与 Linux/amd64、Linux/arm64 的 go vet 均通过；两个 Linux 架构构建均成功。前端/Worker 检查、Shell 语法检查通过。语句覆盖率 16.2%。验证日志保存在 `verification/`。

当前环境仍无法完成 Linux 实机隧道联调和 race 检测。这次只根据用户粘贴的实际输出完成诊断，尚未代替用户部署到 VPS，也没有确认新版本在线运行结果。原报告的其他剩余风险仍适用。

## 在现有“64”VPS 升级

1. 将完整 `fanout-fix409-20261018.zip` 上传到 VPS 的 `/root/`。
2. 在 Termius 的该 VPS 会话执行：

```bash
python3 -m zipfile -e /root/fanout-fix409-20261018.zip /root/fanout409
bash /root/fanout409/2112-main/fanout-main/upgrade-local.sh
```

脚本会重启 fanout，连接会短暂中断；口令、访问路径、订阅与现有节点配置保留，私有备份路径会打印出来。脚本不下载 Go/Xray、不改服务文件、不清空状态、不批量杀掉其他 OpenVPN 进程。请勿通过 F11 再拉取上游 main 覆盖本补丁。

3. 刷新管理网页，点击智能编排。若已有后台任务，应直接看到其进度，不再显示失败 409。程序版本应为 `v3.1.2-orchestrate20261018`，候选预算不超过 64，完成计数应随预检返回而增加。节点全部不可用、出口验证失败或满槽仍会有相应提示；这些不是 409 提示修复能够消除的外部条件。

如果仍异常，提供升级脚本最后输出、当前编排状态和最新 40 条服务日志；不要提供口令或密钥。
